# Aegis Relay

> A server–client relay bridge for cloud-to-enterprise connectivity. A
> dependency-free C client reaches a cloud backend through an explicit,
> observable bridge boundary — the junction where real deployments enforce
> authentication, quotas, and routing.

## Overview

Aegis Relay demonstrates the connective tissue between an enterprise client
and a cloud backend. The client is a single-file C program (WinSock2, zero
third-party dependencies) that speaks HTTP. The server is a minimal Python
stdlib HTTP endpoint. Between them sits the **relay bridge** — the boundary
at which authentication, quotas, and routing would be enforced in a
production deployment.

The bridge is modeled deliberately: both sides are observable, the payloads
that cross the boundary are explicit, and the whole system starts in two
commands. It is a working reference for how the two halves of a
server–client integration fit together.

## Quick start

```bash
# 1. start the server side (fail-loud: requires a shared key)
export AEGIS_SHARED_KEY=change-me-to-a-long-random-string
python3 server/relay_server.py

# 2. in a second terminal, build and run the client
bash build.sh                       # -- or build.cmd on Windows cmd --
dist/client.exe                     # (if a C compiler was present at build time)
```

Every request the client sends is signed with HMAC-SHA256 using the shared
key. The key is resolved on the client as: command line (`client [host] [port]
[key]`) &gt; environment variable `AEGIS_SHARED_KEY` &gt; the compile-time dev
default `aegis-demo-key` (print a warning; dev only).

No compiler on the machine? The client ships as source
(`client/client.c`) with build lines:

```bash
gcc -O2 -o client.exe client.c -lws2_32     # MinGW
cl  client.c ws2_32.lib                      # MSVC
```

The client connects, registers, probes the endpoints, and prints its console
UI with connection status, an event log, and per-request latency. It exits
after the run.

## Architecture

```
 +----------------------------+        +---------------------------+
 |  ENTERPRISE NETWORK        |        |  CLOUD                    |
 |  (the "business" side)     |        |                           |
 |                            |        |  server/relay_server.py   |
 |  client/client.c           |  HTTP  |  GET  /health             |
 |  single-file C UI          +------->+  GET  /ping               |
 |  WinSock2, no deps         |        |  POST /events (handshake) |
 |                            |        |  JSON in, JSON out        |
 +----------------------------+        +---------------------------+
           |                                        |
           +---------- relay bridge boundary ------+
                      (where real deployments
                       enforce auth + routing)
```

## Payload example

A handshake event as sent by the client:

```json
{
  "type": "handshake",
  "client": "aegis-client",
  "client_version": "1.0",
  "event": "client.connected"
}
```

The server's acknowledgment (what the client prints in its status box):

```json
{
  "status": "accepted",
  "event_id": "evt-0001-3f9a21c4",
  "received_at_utc": "2026-10-21T00:12:00+00:00",
  "events_seen": 1,
  "echo": { "type": "handshake", "client": "aegis-client", "client_version": "1.0", "event": "client.connected" }
}
```

## Security

**Request signing (HMAC-SHA256).** Every request to a protected endpoint
carries `X-Aegis-Client`, `X-Aegis-Timestamp` (unix seconds) and
`X-Aegis-Signature`. The signature is

```
hex( HMAC-SHA256( shared_key, "METHOD|path|timestamp|body" ) )
```

computed with a dependency-free SHA-256/HMAC implementation in the C client
(FIPS 180-4 / RFC 4231, tested against the published vectors) and verified
server-side in constant time. The server rejects requests by strict order:
missing/invalid signature → `401`, timestamp skew > 30 s → `401`, replayed
signature+timestamp pair (60 s window) → `403`.

**Rate limiting.** Each client id is limited to 10 requests/minute
(`429` + `Retry-After`).

**Key handling.** The server refuses to start without `AEGIS_SHARED_KEY`
(fail-loud); `AEGIS_ALLOW_INSECURE=1` enables a dev default for local
testing only. The demo key `aegis-demo-key` is a placeholder — set a real
key in any actual deployment.

**Client memory safety.** The C client is audited against a security review:
all message building uses `snprintf` with explicit buffer-size checks; `recv`
is capped into a fixed buffer with explicit null termination and a bound
check on every iteration; the peer-address copy is capped at the target
struct size; ports are range-checked. No `sprintf`/`strcpy`/`strcat` in the
file. The build is warning-clean under `gcc -Wall -Wextra`.
